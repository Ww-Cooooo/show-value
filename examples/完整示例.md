# 完整示例：从开发资料到产品介绍

本页使用虚构小工具“片段匣”。输入背景和摘录都是为演示编写的，不是真实客户案例；附带的程序可以运行。示例展示交付应包含哪些有用信息，不规定其他产品照抄文案或章节。

## 输入：Agent 实际能拿到什么

- [项目说明](note-shelf/README.md)：CLI 读取本地 JSON，按标签筛选摘录并输出 Markdown。
- [实现](note-shelf/shelf.py)：`render_clips` 整理文本；`main` 读取输入并打印结果。
- [示例数据](note-shelf/clips.json)：两条不同标签的摘录，每条含标题、正文与来源。
- [虚构开发记录](note-shelf/development-notes.md)：解释为什么将来源放到每条摘录旁；网页抓取和 PDF 导出只讨论过，尚未实现。

## 第一部分：产品介绍

### 片段匣

片段匣把你已经保存的摘录整理成 Markdown 文字。你可以按标签选出本次写作要用的内容，整理结果会同时保留每条摘录的标题和来源链接。

例如，你存下的资料里既有写作建议，也有演示技巧。这次只想整理写作资料，就用“写作”标签筛选。得到的文字中，每条摘录旁边都有对应来源，回看原文时不必再到另一张清单里逐个找。

这个版本适合已经用 JSON 保存资料、愿意通过命令行处理文字的人。用户准备好摘录后运行一次程序，结果会显示在终端，可以复制到支持 Markdown 的编辑器里继续整理。

片段匣当前不负责从网页收集内容，也没有图形界面或 PDF 导出。它专注于将已经准备好的摘录选出来，并带着来源一起整理为文字。

## 第二部分：亮点与演示依据

### 本次材料与验证范围

对象是同包内的虚构演示程序，没有已发布版本。已查看项目说明、完整示例实现、输入数据与虚构开发记录；2026-09-15 在 Windows 的 Python 3.14 环境运行了全部条目输出和“写作”标签筛选。这里的运行结果只能证明这个小样例，不证明其他产品或其他系统。

### 最值得展示的细节

建议主打：**选出这次要用的摘录，同时保留每条内容的出处。**

这个角度把筛选与来源对应连成一个具体的写作过程。演示只需要两条摘录，就能看出用户选了什么、结果保留了什么；不需要用“智能”“提效神器”代替说明。

| 当前能力 | 对用户的具体价值 | 依据与边界 |
|---|---|---|
| 按标签筛选 | 本次只整理指定主题的摘录，不必把所有资料一起输出 | `shelf.py` 的 `render_clips` 使用标签精确匹配；“写作”样例只输出一条，不是语义检索 |
| 每条摘录保留标题和链接 | 回看来源时，知道该打开哪条链接 | 同一函数为每条摘录生成标题、正文和来源；链接来自输入，程序没有验证网页是否可访问 |
| 输出 Markdown 文字 | 可以复制进后续文档继续编辑 | `main` 打印整理结果；当前不自动保存文件，不代表已集成某个笔记软件 |

### 设计背景与取舍

虚构开发记录里有一个值得解释的调整：最初准备把所有来源放在最后，后来改成跟在各自摘录旁边。原因是作者写作时要回看原文，希望内容与来源能直接对应。

这一理由有记录，也能在当前输出中看见。可以把它作为设计故事；不能由此推导“真实用户一致认为更方便”或“节省了多少时间”。

网页抓取、PDF 导出曾被讨论，但当前实现没有这两项能力，不能放进已实现功能列表。

### 演示怎样安排

先展示两条输入：一条标签是“写作”，另一条是“演示”。随后在 examples/note-shelf 目录执行：

```text
python -X utf8 shelf.py clips.json --tag 写作
```

本次实际输出：

```markdown
## 把示例放在说明旁边

> 先展示读者会拿到什么。
> 再说明完成它需要哪些输入。

来源：https://example.com/writing-a
```

观众应看到：“演示”条目没有进入这次结果；选中的摘录保留了标题、两行正文和来源链接。这里的网址是示例地址，不要拿它演示真实网页内容。

如果还要展示全部资料输出，移除标签参数即可：

```text
python -X utf8 shelf.py clips.json
```

本次运行显示了两条摘录。以上终端步骤已在本机试过；把结果复制到编辑器的画面尚未录制，也没有现成视频素材。

### 可以怎么切入内容

**优先：从一批摘录里准备一份主题资料。** 展示两种标签的输入、筛选动作和带来源的结果，观众能直接判断这是否适合自己的资料整理方式。

**另一个角度：为什么不把来源统一放到文末。** 结合虚构开发记录说明设计取舍，适合讨论小工具的细节。若要另做一份“文末来源清单”对照，应标明这是为了演示新做的排版示意，不能冒充过去实际使用过的版本。

### 仍需确认什么

若把这个小样例继续发展为真实产品，最有价值的后续证据是：让确实使用这类摘录的人，完成一次自己的主题资料整理，看看 JSON 输入方式和输出是否合用。当前没有市场反馈，也没有比较数据；不据样例承诺商业价值、处理速度或广泛兼容性。

## 如果材料不齐，交付会怎样变化

没有开发记录时，仍然可以从程序与输出讲清筛选和来源对应，但不能编写“作者为什么改版”的故事。只有产品说明、没有源码与运行环境时，可以先完成资料支持的介绍，并把能力标为作者陈述；不把这份示例中的实测结论照搬过去。
